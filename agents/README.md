# SOC / SRE agents — modular skills + system prompts

Three agents that operate over the synthetic data in this repo's Splunk indexes (`app`, `infra`,
`security`, generated by [`scripts/datagen/`](../scripts/datagen)), built from **reusable skills** so
tool usage and the data model live in one place instead of bloating every prompt.

| Agent | Goal | Primary index(es) | File |
|---|---|---|---|
| **Threat detection** | Find and characterize attacks; map to MITRE ATT&CK | `security` | [threat-detection-agent.md](threat-detection-agent.md) |
| **Triage** | Rank incidents by severity, correlate signals across indexes, assign an owner | all three | [triage-agent.md](triage-agent.md) |
| **Troubleshooting / RCA** | Root-cause app & infra degradations and propose a fix | `app`, `infra` | [troubleshooting-agent.md](troubleshooting-agent.md) |

## How it's structured — skills vs. agents

Each **agent** file is now just a **short system prompt** (role + the rules unique to it) plus a
config block that references skills by name. The reusable detail lives in [`skills/`](skills), so
"how to use the tools" and "the data model" are written once and shared:

| Skill | Kind | What it covers |
|---|---|---|
| [`tools_splunk_mcp`](skills/tools-splunk-mcp.md) | tools | Splunk search via **`self_mcp`** — `splunk_run_query` / `splunk_run_saved_search` / `splunk_get_indexes`, query idioms |
| [`tools_knowledge_web`](skills/tools-knowledge-web.md) | tools | **`custom_mcp`** — `bedrock_kb_retrieve` (postmortems) + `web_search` (external context) |
| [`reference_data_model`](skills/reference-data-model.md) | reference | the `app`/`infra`/`security` fields + correlation keys + intentional cross-index overlaps |
| [`analysis_standards`](skills/analysis-standards.md) | method | shared rules — evidence grounding, correlation, calibrated confidence, scope |
| [`verify_grounding`](skills/verify-grounding.md) | method | anti-hallucination — a final pass that tool-confirms every claimed id/IP/count and drops unverifiable ones; "no data" over fabrication |
| [`playbook_threat_detection`](skills/playbook-threat-detection.md) · [`playbook_triage`](skills/playbook-triage.md) · [`playbook_rca`](skills/playbook-rca.md) | playbook | each agent's method, SPL cookbook, and output format |

Every agent attaches the five shared skills (`tools_splunk_mcp`, `tools_knowledge_web`,
`reference_data_model`, `analysis_standards`, `verify_grounding`) plus its own `playbook_*`. Edit a tool skill once and
all three agents pick it up. The two MCP connections are `self_mcp` (Splunk search) and `custom_mcp`
(KB + web) — see [`../mcp/README.md`](../mcp/README.md) for standing them up so AgentCore can reach them.

The data model and cross-index correlation keys the agents rely on live in
[`reference_data_model`](skills/reference-data-model.md) (e.g. `INFRA-2026-0001` on node `k8s-node-3`
is the root cause of `APP-2026-0004`; `INFRA-2026-0003` on `pg-primary-1` causes `APP-2026-0002`).

## Generate the data first

```bash
# eyeball without a Splunk:
python3 scripts/datagen/security_datagen.py --dry-run --duration-min 60 | head

# backfill 60 min into Splunk HEC (reuse the datagen HEC token from lib.sh / your instance):
export HEC_URL=https://<splunk>:8088/services/collector/event HEC_TOKEN=<datagen-token>
for g in security app infra; do
  python3 scripts/datagen/${g}_datagen.py --mode backfill --duration-min 60
done
# ...or run one live:  python3 scripts/datagen/security_datagen.py --mode live --interval-sec 30
```

Or simulate the whole thing (populate events + invoke the agents) with
[`run_scenario.py`](run_scenario.py) — see [Simulate a run](#simulate-a-run) below.

## Using the definitions

- **Agent files** ([`*-agent.md`](.)) — a short `## System prompt` (blockquote) plus an
  `<!--agent … -->` config block (name, `llm_connection`, `mcp_connections`, `skills`, settings).
- **Skill files** ([`skills/*.md`](skills)) — a `<!--skill … -->` block plus a markdown body (the
  skill text injected into the agent). Reused across agents.

Everything is model-agnostic and **checked into the repo** — the skills are no longer trapped in
Splunk's KV Store; [`apply-agents.py`](apply-agents.py) reads these files and pushes them up.

## Create & operationalize the agents (from scratch)

The canonical, end-to-end procedure. An AITK agent is **AWS Bedrock AgentCore-backed** — its runtime
is provisioned by the UI **Create** action (a raw KV insert only makes a *Draft* with no runtime). So
the **connections + skills are scripted**, and each **agent is created once in the UI** with the exact
settings below. An agent's tools come **only** from the MCP connections + skills you attach — there is
**no built-in Splunk search**; an agent with nothing attached hallucinates (invents ids/IPs).

### Step 1 — MCP server + reachability (once)

AITK agents run on AgentCore **outside your VPC**, so the MCP endpoints must be reachable from there.
Deploy the MCP server with the load balancer (full walkthrough: [`../mcp/README.md`](../mcp/README.md)):

```bash
# mcp/mcp.env:
CreateLoadBalancer=true
CloudConnectRegion=<your Cloud Connect region>   # e.g. us-east-1 — NOT necessarily the deploy region
SplunkMcpInstanceId=<splunk host instance-id>    # exposes self_mcp (:8089) on the same NLB
# then:
bash mcp/deploy-mcp.sh
```

Record the two stack outputs — they're the MCP connection URLs in Step 2:
- `McpLoadBalancerEndpoint`      → `https://<nlb>:8000/mcp`            (for `custom_mcp`)
- `SplunkMcpLoadBalancerEndpoint` → `https://<nlb>:8089/services/mcp`  (for `self_mcp`)

> The LB must allow your **Cloud Connect region's** Agent Launchpad IP (set by `CloudConnectRegion`),
> **not** the deployment region — else agents fail with "Unable to connect to custom_mcp … after 4 retries".

### Step 2 — Create the connections (AITK → Connections)

**a) LLM connection** — Bedrock, Claude Sonnet. Name it **`bedrock_claude_sonnet`** (or match the name
in the agent files). Use an on-demand **inference-profile** model id (e.g. `us.anthropic.claude-...`).

**b) MCP connections** — *Connections → MCP → Create Splunk MCP connection*, twice:

| Connection | MCP url | Bearer token | Tools |
|---|---|---|---|
| `self_mcp` | `SplunkMcpLoadBalancerEndpoint` (`…:8089/services/mcp`) | the Splunk MCP token (`SplunkMCPToken`, from the Splunk MCP server app) | `splunk_run_query`, `splunk_run_saved_search`, `splunk_get_indexes`, … |
| `custom_mcp` | `McpLoadBalancerEndpoint` (`…:8000/mcp`) | `aws secretsmanager get-secret-value --secret-id mcp-server-mcp-auth-token --query SecretString --output text --region <region>` | `bedrock_kb_retrieve`, `web_search` |

### Step 3 — Push the skills to KV (once)

```bash
./agents/push-skills.sh          # syncs agents/skills/*.md into the aitk_agent_skills KV collection
```

### Step 4 — Create each agent (AITK → Apps → AI Toolkit → Agents → Create)

Fill the Create-Agent form with these exact values. **Name** is the runtime name (what
`run_scenario.py` / `| aiagent` calls); the *System prompt* row names the file to paste. Click
**Create** — this provisions the AgentCore runtime (state → **Available**). These values are the source
of truth in each agent file's `<!--agent … -->` block; `python3 agents/apply-agents.py --list` prints them.

| Field | Threat detection | Triage | RCA / troubleshooting |
|---|---|---|---|
| **Name** | `threatdetection` | `triage` | `rcatroubleshooting` |
| Description | see [threat-detection-agent.md](threat-detection-agent.md) | [triage-agent.md](triage-agent.md) | [troubleshooting-agent.md](troubleshooting-agent.md) |
| Runtime type | AWS AgentCore | same | same |
| LLM connection | `bedrock_claude_sonnet` | same | same |
| System prompt | paste `agents/prompts/threatdetection.txt` | `triage.txt` | `rcatroubleshooting.txt` |
| MCP connections | `self_mcp` + `custom_mcp` | same | same |
| Skills | `tools_splunk_mcp`, `reference_data_model`, `tools_knowledge_web`, `analysis_standards`, `verify_grounding`, **`playbook_threat_detection`** | …same five + **`playbook_triage`** | …same five + **`playbook_rca`** |
| Response variability (temperature) | `0.7` | `0.5` | `0.4` |
| Max tokens | `50000` | `50000` | `50000` |
| Maximum result rows | `10` | `10` | `10` |
| Reasoning effort | `NONE` | `NONE` | `NONE` |
| Agent timeout (s) | `450` | `450` | `450` |

### Step 5 — Verify

```bash
python3 agents/run_scenario.py --mode aiagent --mcp-token "$SplunkMCPToken" --admin-password "$PW"
```
It backfills events and invokes all three agents (details: [Simulate a run](#simulate-a-run)). An
operational agent **cites real data** — `THREAT-2026-00xx`, real IPs, `INFRA-2026-xxxx`. Fabricated
ids mean its MCP connections/skills aren't attached.

**Failure signatures:**
- `Unable to connect to custom_mcp … after 4 retries` → the LB isn't allow-listing your **Cloud
  Connect region** IP. Fix `CloudConnectRegion` (Step 1) or add the IP to the **LB** security group
  with [`../utils/whitelist-agentcore-ips.sh`](../utils/whitelist-agentcore-ips.sh).
- `Cloud Connect details relay returned HTTP 500` → transient Splunk relay flakiness (~1 in 3 invokes). Retry.

> **Why the MCPs need the NLB** (Step 1): AITK agents run on AgentCore **outside your VPC**, so a
> private-IP MCP URL fails at runtime and a public *instance* IP fails at in-VPC connection setup
> (hairpin). One internet-facing **NLB + a private-DNS override** gives a single `https://` URL both
> sides reach; `self_mcp` reuses the same NLB on `:8089`. Detail + reproducer:
> [`../mcp/README.md`](../mcp/README.md#reachability-from-aitk-agents-bedrock-agentcore),
> [`test-agentcore-mcp.py`](test-agentcore-mcp.py) → [`reports/`](reports).

## Simulate a run

[`run_scenario.py`](run_scenario.py) does the end-to-end demo: check the three agents exist →
**populate events** (backfills `security`/`app`/`infra` via datagen) → **invoke the agents** and write
a report. It needs the Splunk **MCP (`:8089`) and HEC (`:8088`) as localhost**, so it must run **on the
Splunk host** — HEC isn't reachable off-box, so it can't fully run from a laptop.

**From a laptop → use the wrapper** [`run-scenario.sh`](run-scenario.sh): it runs the scenario on the
host via SSM and downloads the timestamped report to `agents/reports/`. It auto-resolves the host
(SplunkAiRole=gpu-host tag), and the tokens from `config/cloud.env`:

```bash
./agents/run-scenario.sh                       # populate + invoke all three, fetch the report
./agents/run-scenario.sh --mode playbook       # SPL-only (no LLM)
./agents/run-scenario.sh --duration-min 90 --skip-datagen   # extra args pass through
```

**On the Splunk host** → run the script directly:

```bash
python3 agents/run_scenario.py --mode aiagent \
  --mcp-token "$SplunkMCPToken" --admin-password "$PW"
# writes agents/reports/scenario-report-<timestamp>.md  (add --out <path> to pin an exact filename)
# --mode playbook runs each agent's SPL directly (no LLM) — useful when the aiagent relay is down.
```

The intermittent `Cloud Connect relay HTTP 500` is retried automatically (`--retries`, default 3).

- **`--mode aiagent`** (default) invokes `| aiagent agent_name="X" prompt="<role task>"` through the
  Splunk MCP, exercising the agent's real LLM + attached skills/tools. For grounded output the agent
  must have its MCP connections + skills attached (the recipe above) — otherwise it has no tools and
  will hallucinate.
- **`--mode playbook`** runs each agent's SPL cookbook directly via `splunk_run_query` — deterministic
  signal with no LLM, handy to confirm the data before invoking the agents.

Reports land in [`reports/`](reports), one per run: **omit `--out`** and it auto-writes a timestamped
file `scenario-report-YYYYmmdd-HHMMSS.md` (so runs don't overwrite). Pass `--out <path>` only when you
want an exact filename.

## Audit a report for hallucinations

Two layers guard against hallucination:

- **Prevention (in-agent):** the [`verify_grounding`](skills/verify-grounding.md) skill makes each
  agent tool-confirm its own claims and prefer "no data" over fabrication.
- **Proof (external, optional):** [`check-hallucinations.py`](check-hallucinations.py) independently
  verifies that every entity an agent cited actually exists in Splunk. It extracts the incident/threat
  ids, IPs, and MITRE ids from a report (or piped text) and runs one confirming query per token
  (`search index=* "<token>" | head 1`); tokens that return nothing are flagged.

```bash
# audit a report (via the NLB MCP from a laptop):
python3 agents/check-hallucinations.py agents/reports/scenario-report-<ts>.md \
  --mcp-url https://<nlb>:8089/services/mcp --mcp-token "$SplunkMCPToken"
# pipe arbitrary agent text; fail (exit 1) if any index id is fabricated:
pbpaste | python3 agents/check-hallucinations.py --mcp-token "$SplunkMCPToken" --strict
```

**Index-style ids** (`THREAT-`/`APP-`/`INFRA-`) are hard-checked — missing = fabricated. `INC-`
(KB postmortem case ids) and `CVE-` are treated as **KB/external** and listed but not flagged (they
live in the knowledge base, not the indexes). IPs and MITRE ids are reported softly (a real external
IP or a mapped technique legitimately may not be in the data). `--strict` exits non-zero on any
fabricated index id — handy in CI.

## Troubleshooting agent invocations

Invoking agents **from a laptop through the NLB** is reliable for *short* calls (tool enumeration,
`READY` probes, `check-hallucinations.py` queries) but flaky for *full* agent runs. Two distinct causes:

| Symptom | Cause | Fix |
|---|---|---|
| Long runs "return no response" / connection reset (esp. the slower agents) | The **NLB's TCP idle timeout is a fixed 350s** (not configurable). An `aiagent` call holds the connection *idle* while the agent thinks; runs > ~350s get cut over the NLB. | **Run on the Splunk host** — `./agents/run-scenario.sh` (or run `run_scenario.py` on-box). localhost has no NLB in the path, so no 350s cap. |
| Fast failure (~10–15s) with `Cloud Connect details relay returned HTTP 500` | Intermittent Splunk Cloud Connect relay flakiness (~1 in 3 invokes). | **Retry.** `run_scenario.py` does this automatically (`--retries`, default 3). |
| `Unable to connect to custom_mcp … after 4 retries` | The LB isn't allow-listing your **Cloud Connect region** IP. | Set `CloudConnectRegion` and redeploy, or add the IP to the LB SG ([`../utils/whitelist-agentcore-ips.sh`](../utils/whitelist-agentcore-ips.sh)). See [`../mcp/README.md`](../mcp/README.md). |
| Agent replies but invents ids/IPs | No MCP tools attached, or ignoring grounding. | Attach `self_mcp` + `custom_mcp` + `verify_grounding` (see the operational checklist); audit with [`check-hallucinations.py`](check-hallucinations.py). |

**Bottom line for laptop use:** don't drive multi-minute agent runs over the NLB — use
`./agents/run-scenario.sh`, which runs them on the host (no 350s cap) and retries the transient 500s.
The NLB path stays perfect for the connection *setup* (tool enumeration) and short queries.

Other levers: agents already run **one at a time** (never in parallel). To ease the relay further,
space them out and/or isolate one — these work on `run_scenario.py` and pass straight through
`run-scenario.sh`:

```bash
./agents/run-scenario.sh --pause-between 15                 # wait 15s between agents
./agents/run-scenario.sh --agents threatdetection          # invoke a single agent (isolate / retry one)
./agents/run-scenario.sh --agents triage --pause-between 20 # combine
```

`run_scenario.py` also retries the transient 500 (`--retries`) and prints a per-agent
`ok/FAIL` summary at the end. Lowering `max_tokens` / narrowing the task shortens a run (helps stay
under the NLB's ~350s cap), but the reliable fix for long runs remains the host path above. (An ALB
has a configurable idle timeout, but it terminates TLS and needs a real cert/domain — the NLB was
chosen to avoid that; the host path is simpler.)
